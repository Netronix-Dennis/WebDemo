本助手已完成建置並發布上線（僅限邀請），供資訊部與需求端試用。以下說明定位、核心流程、實測結果與後續規劃。

1一句話定位與現況

把使用者模糊的一段話（「想把費用請款 E 化」「主管要看某報表」），透過 AI 對談潤飾與結構化，轉成 MIS 可受理的電子簽核需求單——含表單欄位與簽核流程推論，並可輸出 JSON。
✅ GPT 已發布上線（僅限邀請） ✅ 五區塊需求單 + 簽核推論 + JSON 匯出 實測通過 ✅ 核決權限級距推論（可推論、不整表輸出） ✅ 對齊 Lelina 平台 v4 規格逐項吻合 📋 待與 Lelina 對焦平台 JSON schema 銜接

2需求背景與戰略價值

需求源自資訊部 Lelina（軌2 評估 #18）。她已自建 HTML 原型平台《MIS AI 資訊需求細化平台 v4》，流程與缺口都想清楚了——她自己點名的缺口是：原型偏規則式（關鍵字判斷），缺「需求理解引擎」（反問／潤飾／缺漏判斷／語意分類）。
本 GPT ＝ 她平台缺的「需求理解引擎」的活原型。指令在 GPT 裡疊代成熟後，同一套 prompt 可包成 API 供她平台呼叫（她 roadmap 的「規則庫＋AI API 混合」階段）——軌2 GPT 直通軌3 服務化。

3核心流程（對齊 Lelina 平台）

原始需求 → AI 潤飾「我理解你的意思是…」 → 使用者確認／修正 → 拆五區塊需求單 → 簽核流程推論 → 輸出 JSON。紀律沿用她的原則：AI 推測需標示、不覆蓋使用者已修內容、決策由人。
五區塊需求單
  • ① 說明（E 化目的與效益）
  • ② 表單畫面設計（分區建議）
  • ③ 表單欄位（＊必填 + 型態/來源）
  • ④ 簽核流程（含推論依據）
  • ⑤ 其他 + 待確認項目
關鍵行為
  • 先潤飾確認，確認前不拆（避免拆錯方向）
  • 金額／請款 → 自動加「核決權限」關卡與金額欄位
  • AI 推測一律標「（推測，請確認）」
  • 可用 Code Interpreter 產出可下載 JSON

4端到端實測（以 Lelina 簡報標準範例：費用請款）

用她簡報第 7 頁的標準範例（費用請款）把助手完整跑一遍。以下為實際對話摘要。

使用者
想把「費用請款」E 化，改用電子簽核。需要填金額、發票、專案代碼，簽核要經過主管、財務，再依金額跑核決權限。
AI 助手
我理解你的意思是：把費用請款流程 E 化，目的在減少紙本、方便追蹤，並依金額自動套用核決權限。初步簽核順序：申請人送出 → 主管 → 財務審核 → 依金額對照核決權限逐級簽核。這樣理解對嗎？有要修正的地方嗎？
使用者
對，就是這個意思。補充：A 公司、財務部、王小明，金額約 8 萬。請整理成完整五區塊需求單。
AI 助手
（輸出完整五區塊需求單，見下方）
③ 表單欄位（節錄）
欄位型態來源／預設備註
＊申請人人員系統登入者自動帶入系統自帶
＊申請金額金額使用者輸入作為核決權限判斷依據
＊發票附件附件使用者上傳必填，支援 PDF／圖片
＊專案代碼文字／下拉 (推測，請確認)使用者輸入建議可串接專案主檔
申請原因多行文字使用者輸入(推測，請確認)
④ 簽核流程
關卡簽核角色關卡規則
第1關 開單者申請人建立並送出申請
第2關 開單者主管申請人直屬主管審核請款內容
第3關 財務審核財務人員確認金額、發票附件及專案代碼
第4關 核決權限依公司核決權限表依申請金額自動逐級簽核
核決權限推論（示範）：本案金額約 8 萬元，屬費用動支情境，約需簽至總經理層級；（推測，請確認）實際級距與簽核人仍以貴公司最新核決權限規定為準，不於系統中寫死。

6資料與資安

  • 知識庫：空白需求表單格式、簽核規則庫（核決權限表整理成級距規則）、期望產出樣式、核決權限表原檔。
  • 核決權限表為內部制度：助手可依它做簽核層級推論、但不整表輸出原文；分享範圍僅限邀請、給資訊部／需求端。

7後續規劃

  • T9 reportError 實打：確認錯誤回報動作端到端通（會寄一封測試通知信）。
  • 與 Lelina 對焦（15–20 分）：平台 JSON schema 銜接、源碼邏輯，鋪路把指令包成 API 供她平台呼叫（軌2 直通軌3）。
  • 依試用回饋，持續補強電子簽核常見表單／流程模板。
