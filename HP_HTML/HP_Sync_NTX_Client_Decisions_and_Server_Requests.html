1.5 · 請留意「32 MiB」是編碼字元數，實際檔案是 24 MiB

Server 的 32 MiB 限制指的是 Base64 編碼後的字元數（33,554,432 字元），不是檔案大小。
Base64 會把 3 個位元組展開成 4 個字元，因此對應的實際 .ent 檔上限是 24 MiB：

33,554,432 × 3 / 4 = 25,165,824 bytes = 24 MiB

對使用者真正有意義的數字是 24 MiB（實際檔案）；
建議兩邊文件都標明「編碼 32 MiB 字元 = 實際 24 MiB 檔」，避免持有 30 MiB 檔的使用者誤以為在 32 MiB 上限內。

    被略過的筆記會在 Android 缺席，Server／Windows 端不會收到訊號。
    共九種觸發條件：
    • id 非標準 UUID 格式（invalid note id）
    • 缺少 deleted 欄位（missing deleted flag）
    • 活躍筆記缺少 title 或 createdAt，或 createdAt < 0（incomplete live note）

    • 解碼後超過 25,165,824 bytes（超過 §1.5 的 24 MiB 上限）
    • 解碼結果不是可讀取的 ZIP，或不含任何 entry（ENT ZIP is empty）
    • ENT 含多於一頁、含任何附件、或含 nNote 無法呈現的內容
    • 超出 §1.6 的 ZIP 防護限制
  • 1.4 單頁範圍：目前上傳與下載均只接受單頁 ENT、不含附件（Stage 1 簡化）；

  • 1.6 ZIP 防護：nNote 自訂三項壓縮檔防護：
    • 解壓後總量上限 64 MiB
    • 單一 entry 解壓後上限 64 MiB
    • 每個套件的 entry 數上限 32
  • 1.7 整批失敗條件：下列三種情況會使整次 pull 失敗（而非略過單筆），一般 Server 不會產生：

    • 同一批出現重複 UUID（同一主鍵兩列，代表資料完整性破損）
  • 1.8 略過與重試：被略過的筆記仍會推進 watermark。
    • 若 HP 日後修正某筆 payload，煩請一併指派新的、嚴格遞增的 updatedAt，nNote 才會重新抓取。
    • NTX 端也會加上「隔離重試清單」，讓壞筆記不致永久缺席。

HP Sync: NTX Notifications & A Few Points for HP

0. Overall Status

Functionality is in place and sync works.
NTX's client-side work (including the previously reported memory issue) is complete.
This document is mostly a notification of decided client behavior; only the three points below need HP's attention or reply.

Note: scale / large-file / transfer-interruption items are post-GA and out of scope for the current POC stage, so they are not covered here.

1. Points for HP's Attention / Reply

1.3 · needs replyWhat should the content field carry?

We are still unsure what the content string field is expected to hold.
nNote currently drops content on pull and sends content: "" on upload, because nNote itself has no plain-text content to put there.
Please clarify the intended use and formal semantics of content.

Side note: sending "" on upload may overwrite a description originally authored on the Windows side;
once the intended use is clear, we can decide whether to preserve and echo it back.

1.5 · please note"32 MiB" is encoded characters; the actual file is 24 MiB

The Server's 32 MiB limit is a count of Base64-encoded characters (33,554,432 chars), not a file size.
Base64 expands 3 bytes into 4 characters, so the corresponding actual .ent file limit is 24 MiB:

33,554,432 x 3 / 4 = 25,165,824 bytes = 24 MiB

The number that is meaningful to a user is 24 MiB (the actual file);
we suggest both sides' docs state "32 MiB encoded chars = 24 MiB actual file," so a user holding a 30 MiB file doesn't assume it is within a 32 MiB limit.

1.9 · please keepKeep the port configurable

On our test laptop, 8080 is already taken by another process, so we set the service to 8081 via [server] port in config.ini, and it works.
Please keep [server] port a supported setting in future packages; don't hard-code or force 8080.
This is an NTX test-environment need; the actual deployed users remain on the HP side.

docs · requestA Swagger / OpenAPI spec would help

Going forward, we'd appreciate a Swagger / OpenAPI specification for the Server API.
NTX is more familiar with that structure and can more clearly see each field's definition:

  • the request/response shape of each endpoint;
  • each field's name, type, and whether it is required;
  • the formal definition and semantics of fields like content / inkContent;
  • the mapping of error and status codes.

This would also resolve most of the field-definition questions in this document at once (e.g. content in §1.3).

2. NTX Notifications (FYI - no action needed)

The following are decided client-side behaviors, shared for HP's awareness; no action from HP is needed.

  • 1.1 Silent skip: on a validation-failing note, nNote skips it and continues the batch (so one bad record doesn't block all future pulls).
    A skipped note is absent on Android, with no signal to the Server/Windows side.
    Nine conditions trigger a skip:
    • id is not a standard UUID (invalid note id)
    • missing deleted field (missing deleted flag)
    • a live note missing title or createdAt, or createdAt < 0 (incomplete live note)
    • a live note's inkContent is null (note has no ink content)
    • non-canonical Base64, or length not a multiple of 4 (Base64 is not canonical)
    • decoded size over 25,165,824 bytes (over the §1.5 24 MiB limit)
    • decoded result is not a readable ZIP, or has no entries (ENT ZIP is empty)
    • ENT has more than one page, any attachment, or content nNote cannot render
    • exceeds the §1.6 ZIP guards
  • 1.4 Single-page scope: upload and download currently accept single-page ENT only, no attachments (a Stage 1 simplification); multi-page is deferred to GA.
  • 1.6 ZIP guards: nNote applies three archive guards:
    • total inflated size limit 64 MiB
    • per-entry inflated size limit 64 MiB
    • up to 32 entries per package
  • 1.7 Batch-fail conditions: the three cases below fail the whole pull (rather than skipping one); a normal Server should not produce these:
    • a null element in the changes list
    • any note with a missing or negative updatedAt
    • a duplicate UUID in one batch (two rows for one key = a data-integrity break)
  • 1.8 Skip & retry: a skipped note still advances the watermark.
    • If HP later fixes a note's payload, please also assign a new, strictly-increasing updatedAt so nNote re-fetches it.
    • NTX will also add an "isolated retry list" so a bad note is not permanently absent.

3. Summary

Functionality is in place and sync works; NTX's client-side work is complete.
Points that need HP's attention or reply:

  • 1.3 what the content field should carry;
  • 1.5 "32 MiB" is encoded characters, with a 24 MiB actual-file limit;
  • 1.9 please keep [server] port configurable;
  • Docs a Swagger / OpenAPI spec would be appreciated.

Everything else is a notification of NTX behavior and needs no HP action.
