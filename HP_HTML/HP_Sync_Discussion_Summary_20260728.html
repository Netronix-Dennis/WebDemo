2. 格式結構差異分析 本週最主要技術發現

Gourav 提供 HP Windows App 產出的檔案請我方驗證匯入,實測無法直接匯入 nNote；
經逐 byte 分析確認原因如下:

HP 端樣本(<uuid>.entinfo)我方 nNote 產出(.entinfo)
檔頭 magicHWPENKITDATAENTPAGEINFO
實際內容裸的單頁墨跡資料(等同一頁 .ent,只是副檔名叫 .entinfo)筆記本層容器:定義頁面關係、內嵌所有頁的墨跡
多頁能力❌ 一檔一頁✅ 天生支援多頁
關鍵結論:兩邊同用 .entinfo 副檔名,內容物卻是不同層級的東西；
但最底層的墨跡資料格式(HWPENKITDATA)完全相同,HP 樣本可正常解析出手寫筆畫(兩份各 5、8 筆) - 差異只在包裝層,互通缺口小。
  • 對策:nNote 匯入端加 magic 檢測分支(讀到 HWPENKITDATA 即走 standalone ink 匯入路徑),改動小,可同時支援兩種格式。

HP Sync Discussion Summary

2026-07-23 – 07-28　|　Alignment progress with Gourav (HP Connectivity)　|　Netronix
This week: we completed a structural comparison of HP's and our .entinfo files and confirmed the difference is only at the packaging layer (the ink data layer is compatible);
the inkContent format for both Demo / CES stages is defined;
and we received new information from FluxInk that the AIE SDK's container file has been renamed to .inkF - confirmation requested from HP by mail.

1. Demo-Stage Contract Locked confirmed

Confirmed by Gourav on 07-27:

  • Field mapping: content = plain-text description; inkContent = FluxInk payload (Base64). Server stays opaque (no content parsing); the Windows client materializes files from inkContent.
  • Size ceiling: 8 MiB → 32 MiB (in the next build); oversize returns 413. The final GA limit is TBD by HP after more real-world testing.
  • Slim tombstones: only id + deleted + updatedAt, body fields empty/null - already live in v1.1.20260723.2.
  • Pagination: Demo keeps the current bare changes?since= list; deferred to GA.
Significance: the P0 issues raised in our 7/21 one-page brief (full tombstone bodies, undefined size ceiling) are now formally closed - the Server side has been fixed per our recommendation and is live.

2. File Structure Analysis key technical finding

Gourav shared files generated by the HP Windows App for import validation. They could not be imported into nNote directly;
byte-level analysis identified the cause:

HP sample (<uuid>.entinfo)Our nNote output (.entinfo)
Magic headerHWPENKITDATAENTPAGEINFO
Actual contentBare single-page ink data (equivalent to one .ent page, just named .entinfo)Notebook-level container: defines page relationships and embeds the ink of all pages
Multi-page❌ one file = one page✅ natively multi-page
Key conclusion: both sides use the .entinfo extension, but the contents are different layers of the format. The underlying ink data format (HWPENKITDATA) is identical - HP's samples parse correctly (5 and 8 strokes respectively) - so the gap is only at the packaging layer and is small.
  • Action: add a magic-detection branch to nNote's import (route HWPENKITDATA content to the existing standalone-ink import path) - a small change that makes nNote accept both formats.

3. Demo / CES Format Definition confirmed

StageWindows sideinkContent payload
DemoFluxInk Windows App (existing product, no export function).entinfo (container, Base64)
CESHP's Note App (developed by HP on the FluxInk AIE SDK).ent (single page, Base64)

nNote can produce either format and will switch per stage.

4. New Info: AIE SDK Container Renamed to .inkF pending confirmation

  • Our FluxInk contact (Selena) informed us that the AIE SDK's container output has been renamed from .entinfo to .inkF (same ENT format, name change only); the FluxInk Windows App used for the Demo still uses .entinfo.
  • .inkF corresponds to our current .entinfo container.
If Gourav confirms the AIE SDK outputs .inkF: the CES-stage inkContent should likely carry the container format instead of a bare .ent - which would also cover future multi-page support. Confirmation mail sent on 07-27.

  3. Whether the AIE SDK outputs .inkF (confirmation from section 4).
  4. Gourav's ownership scope - Connectivity Server only, or the Windows client app as well (determines who we align with on the long-term format decision).
