In one line:
deleted notes still retransmit their full content and saturate the sync stream.

After a note is deleted, the Server keeps the tombstone's full content.
During first sync, manual reset, or any full-history replay from since=0, the Server retransmits the complete content of all historical tombstones.

For a tombstone, the client needs only id, deleted, updatedAt, and required metadata - not the original content.

4. Acceptance & Scope

P0 acceptance

Objectively verifiable

  • Existing tombstone content drops from 24.67 MiB → ≈ 0;
    the whole response falls well below 28.83 MiB and tombstone share approaches 0%.
  • All 7 live content values remain byte-identical after the fix.
  • id, deleted, updatedAt, watermark, and same-id POST revival semantics remain unchanged.
  • Requests above the agreed ceiling return a stable 413 with no partial write.
Scope guard

Not requested from the Server

  • Parse/understand the ENT internal format, or implement an NTX handwriting parser.
  • Remove all tombstone history, or change updatedAt > since / same-id POST revival behavior.
  • Treat the 3.86 MiB sample or provisional 6/8 MiB guards as permanent product limits before a joint decision.

NTX client side:
streaming parse (no full JSON DOM), discard tombstone content after parsing, cancellable HTTP, diagnostics, atomic failure without watermark advance, page-by-page apply once paginated.
But the client cannot eliminate Server bytes or make an unpaginated response resumable.

P0 · 阻斷

墓碑重傳整包原始內容

P0 · Blocker

Tombstones retransmit the full content

白話比喻

想像你把一份 100 頁的文件丟進碎紙機（刪除）。
但每當你要求系統「從頭對一次帳」（初次同步或重置）時，它還是把整份 100 頁一字不漏念一遍，只為了最後告訴你一句「這份已經丟了」。
你真正需要的，只是「哪一份丟了」這句話而已。

為什麼是問題

本次量測（changes?since=0）29 筆裡，有 22 筆是這種「已刪除卻仍夾帶全文」的紀錄，佔了整包流量的 85.56%。
每次從 since=0 的完整重播（初次同步、manual reset、狀態重置）都會再發生一次，不會自己消失。
在 e-ink 平板 ＋ 弱 Wi-Fi 下，這讓一次重置卡了約 6 分鐘。

怎麼修

  • DELETE 時就把內容清空；
    或保留在資料庫、但回傳時省略內容。
  • 單這一項，就能把這批資料從 28.83 MiB 降到約 4.16 MiB（−85%）。

Plain-language analogy

Imagine you shred a 100-page document (a delete).
But every time you ask the system to reconcile from scratch (a first sync or a reset), it still reads all 100 pages aloud word-for-word, only to finish with one sentence: "this one is gone."
All you actually needed was that one sentence.

Why it matters

In this measurement (changes?since=0), 22 of 29 records are these "deleted but still full-text" entries, making up 85.56% of the payload.
It recurs on every full replay from since=0 (first sync, manual reset, state reset) and never goes away on its own.
On an e-ink tablet over weak Wi-Fi, this stretched one reset to about 6 minutes.

The fix

  • Clear the content on DELETE, or keep it in the DB but omit it in the response.
  • This one change alone takes this dataset from 28.83 MiB down to about 4.16 MiB (−85%).
P0 · 阻斷

既有資料庫也要清理

P0 · Blocker

Existing database also needs cleanup

白話比喻

就算今天起規定「以後刪除的文件不再念全文」，
資料庫裡「之前」已經刪除的那 22 份，全文還是躺在裡面。
下次對帳照樣被念出來 - 所以得另外派人去把舊紀錄的全文擦掉。

為什麼是問題

只修「未來的刪除」不能改善「現在這台機器」。
現有 instance 不清，每次 since=0 測試還是 28.83 MiB，問題依舊。

清理時不能踩的底線

  • 7 份還在使用的筆記內容一個位元組都不能動（要能驗證一字不差）。
  • 刪除標記、時間戳、之後重新寫入可「復活」的能力都要保留。
  • 要講清楚清理會不會改動時間戳 - 這會牽動下一項「排序安全性」。

Plain-language analogy

Even if from today "future deletes no longer read the full text,"
the 22 documents deleted earlier still have their full text sitting in the database.
They get read aloud at the next reconcile anyway - so someone has to go wipe the old records' text.

Why it matters

Fixing only "future deletes" does not fix "this machine today."
If the existing instance is not cleaned, every since=0 test is still 28.83 MiB.

Non-negotiables during cleanup

  • The 7 live notes' content must stay byte-identical (verifiable).
  • Keep the delete flag, timestamp, and the ability to "revive" via a later write.
  • State whether cleanup changes the timestamp - it feeds the next item, "ordering safety."
P0 · 會議定案

單筆大小上限沒有共識

P0 · decide in meeting

No agreed per-note size limit

白話比喻

兩邊對「一份筆記最多可以多大」沒有共識。
就像貨運沒講清楚單件包裹的重量上限 - 結果超大包裹有時被收、有時被拒，行為不一致。

三個容易混淆的尺寸

  • 原始 ZIP（decoded）：筆記本身，我方門檻 6 MiB。
  • 編碼後（encoded）：塞進 JSON 要先 Base64，體積膨脹約 33%，我方門檻 8 MiB。
  • 完整封包：還要加標題與 metadata，所以「封包上限」一定大於「內容上限」，不能混為同一個數字。

現況的矛盾

我方 App 自訂的 6／8 MiB 只是暫行值；
Server 到底能吃多大沒人確認，測試時甚至發現它默默存下一筆 16 MiB（我方門檻的兩倍）。
代表三方（App 門檻、Server 實際上限、產品正式契約）根本沒對齊。

要 HP 給的

  • 保證至少吃下所有「編碼後 ≤ 8 MiB」的內容。
  • 講清楚內容與封包各自的上限。
  • 超過上限時回穩定的 413，且絕不寫入一半。

Plain-language analogy

The two sides never agreed on "how big a single note can be."
It's like a courier with no stated per-parcel weight limit - oversized parcels sometimes get accepted, sometimes rejected. Inconsistent.

Three easily-confused sizes

  • Raw ZIP (decoded): the note itself; our guard is 6 MiB.
  • Encoded: to fit in JSON it is Base64-encoded, which inflates ~33%; our guard is 8 MiB.
  • Full request body: plus title and metadata, so the "body ceiling" must exceed the "content ceiling" - not the same number.

The contradiction today

Our 6/8 MiB guards are only provisional.
Nobody has confirmed how big the Server accepts; testing even found it silently stored a 16 MiB record (twice our guard).
So all three - app guard, real Server ceiling, product contract - are misaligned.

What we need from HP

  • Guarantee acceptance of every "encoded ≤ 8 MiB" content.
  • State the content ceiling and the full-body ceiling separately.
  • Return a stable 413 when over the limit, with no partial write.
P1 · 正式必需

changes API 需要分頁

P1 · GA-critical

The changes API needs pagination

白話比喻

現在的做法是「把所有東西塞進一個大箱子，一次寄來」。
東西少還好，多了箱子會爆；
而且中途掉一次，就得整箱從頭重寄。

分頁是什麼

把大箱子拆成多個有大小上限的小箱子，每箱附一個「取件號碼」（cursor）。
App 只要原樣帶回號碼要下一箱，掉哪箱補哪箱，不必整批重來。

為什麼還要「固定終點」

App 分好幾箱下載期間，Server 可能又收到新資料。
先框定「這一輪只寄到這裡」（snapshot boundary），新資料留到下一輪 - 才不會邊寄邊變，造成漏寄或重複。

提醒

App 端的串流解析只能省記憶體，
無法解決傳輸時間、失敗重傳與續傳 - 這幾項只有 Server 分頁能真正解決。

Plain-language analogy

Today it's "put everything in one big box and ship it at once."
Fine with little data; with a lot, the box bursts;
and if the transfer drops midway, the whole box must be re-shipped from scratch.

What pagination is

Split the big box into several size-capped smaller boxes, each with a "pickup number" (cursor).
The app just replays the number to get the next box; if one box drops, only that box is re-fetched.

Why a "fixed end boundary" too

While the app downloads several boxes, the Server may receive new data.
Fixing "this cycle only ships up to here" (a snapshot boundary), with newer data left for the next cycle, prevents the dataset shifting mid-transfer and causing omissions or duplicates.

Note

Client-side streaming only saves memory.
It cannot fix transfer time, re-send on failure, or resumability - only Server pagination can.

P1 · 正式必需（我方可並行規劃）

排序安全性 - 可能無聲漏資料

P1 · GA-critical (NTX can plan in parallel)

Ordering safety - silent data loss risk

白話比喻

每筆筆記有一個「流水號時間戳」，App 靠它記住「我讀到哪了」。
如果有兩筆的號碼剛好一樣，而分頁又剛好切在這兩筆中間，
App 會誤以為兩筆都讀完了，於是無聲無息地漏掉一筆。

為什麼危險

這種漏抓不會報錯、不會當機。
使用者只會發現「有一本筆記莫名不見了」，而且事後極難追查。

怎麼修（HP 擇一）

  • 保證時間戳在所有寫入路徑都全域唯一、嚴格遞增（含 migration、cleanup、還原、未來多台伺服器）；
  • 或規定 page／snapshot boundary 不得切開相同時間戳的 tie group（同一組整批一起送）；
  • 或改用「時間戳＋id」的複合游標。

我方現在可並行的準備

把水位線做成「複合就緒」（不寫死單一 timestamp、預留可容納複合鍵或不透明 token）、套用做成冪等（重複套用無害）、只在整輪成功後才推進水位線 - 這幾項屬 client 內部設計，可先行進行。
但 cursor 的具體處理仍須待 HP 的 cursor／分頁契約定案；
我方先做好準備，等契約確定即可無痛接上、避免重寫。

Plain-language analogy

Each note has a "serial-number timestamp" the app uses to remember "how far I've read."
If two notes happen to share the same number and a page boundary lands right between them,
the app assumes both were read - and silently drops one.

Why it's dangerous

This omission throws no error and never crashes.
The user just finds "a notebook mysteriously vanished," and it's extremely hard to trace afterward.

The fix (HP picks one)

  • Guarantee the timestamp is globally unique and strictly increasing on every write path (incl. migration, cleanup, restore, future multi-instance);
  • or ensure a page/snapshot boundary never splits a tie group sharing the same timestamp (deliver the whole group together);
  • or switch to a "timestamp + id" composite cursor.

What NTX can prepare now, in parallel

Making the watermark "composite-ready" (no hard-coded single timestamp; room for a composite key or opaque token), keeping apply idempotent (re-applying is harmless), and advancing the watermark only after the whole cycle succeeds are internal client choices we can start now.
The exact cursor handling, however, depends on HP's cursor/pagination contract;
we prepare ahead so it slots in without a rewrite once that contract is set.

P1 · 規劃

容量政策與測試資料隔離

P1 · planning

Capacity policy & test isolation

白話比喻

沒有人定義「一個帳號最多能放幾本筆記、刪掉的要保留多久」。
另外，壓力測試用的大檔案被塞進了「正式整合用」的資料庫，刪掉後殘影還留著，永久污染之後每一次測試。

要處理的

  • 共同定義每帳號最大筆數、墓碑保留期限、是否做歷史壓縮。
  • 壓測與異常資料測試改用獨立環境，或測完真正清乾淨。
  • 若目前無法定義最大總筆數，API 就不能假設「所有筆記塞得進一個 response」（呼應分頁那一項）。

Plain-language analogy

Nobody defined "max notes per account, and how long deleted ones are kept."
Also, a large stress-test file was pushed into the "integration" database; after deletion its ghost remained, permanently polluting every later test.

What to settle

  • Jointly define max notes/account, tombstone retention, and whether history is compacted.
  • Move stress and malformed-data tests to an isolated environment, or truly clean up afterward.
  • If no max total can be defined yet, the API must not assume "all notes fit in one response" (ties back to pagination).
P2 · 維運

可觀測性（記錄同步狀況）

P2 · Ops

Observability (log sync activity)

白話說明

目前我方沒有取得足以拆分 Server、網路與 Client 三段耗時的診斷資訊，出事時難以判斷到底哪一步慢、哪一步錯。
（這不代表 Server 內部完全沒有紀錄，只是這些資訊目前未對外提供。）

建議記錄

  • 端點、狀態碼、耗時、回傳大小、筆數、存活／墓碑數、分頁與 cursor 資訊。
  • 逾時／取消／回應過大等分類。
  • 但不記錄敏感內容（API 金鑰、Base64 全文）。

Plain-language

Today we lack the diagnostics needed to split timing across Server, network, and client, so it is hard to tell which step was slow or wrong when something goes off.
(This does not mean the Server has no internal logging - only that such data is not currently exposed to us.)

Recommended to log

  • Endpoint, status code, elapsed time, response bytes, record count, live/tombstone counts, page/cursor info.
  • Timeout / cancel / response-too-large classifications.
  • But never log sensitive content (API keys, full Base64 payloads).

Plain-language

When a brand-new Server database starts, it auto-inserts 12 Markdown demo notes.
Because they are not the ENT format nNote needs, the first sync gets stuck on the first one and the whole batch fails.
Deleting the database and restarting brings the 12 back again.

Framing: known, not a new bug

This is HP's pre-existing test seed data, and HP is already aware of it.
We already work around it - soft-deleting the 12 restores normal sync, verified in testing.
But soft-delete only turns them into 12 tombstones, not a truly clean Server history;
those tombstones are still resent on a since=0 full replay (linking back to the first tombstone issue).

Why raise it anyway

The workaround must be redone every time the DB is recreated or deployed on a new machine.
For a clean, out-of-the-box demo flow, it is worth handling together.

Recommendation

  • Have the partner build clear/disable this seed by default;
    or replace it with a real single-page ENT fixture.
  • Provide a one-time cleanup or migration for existing installs.
