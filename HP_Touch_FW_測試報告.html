一句話結論：FW / driver 把手指與筆分流得完全正確（手指走 finger node、筆走 stylus node）。 手指之所以在 app 出水，是因為 nNote 的「手指攔截」程式碼，被一個寫死機型清單的開關擋住了—— 新裝置不在清單內，攔截整段被跳過。這是 APP 要改，不是韌體要改。

① 底層 ADB Raw Event — 全部正確，問題不在 FW / Driver

所有 testcase 的 raw event 都符合預期。最關鍵的交叉驗證是「手指操作時，筆的 node 完全乾淨」：

檢查實測結果判定
手指操作時，stylus node（筆 / event7）無 BTN_TOUCH、無 ABS_PRESSURE正確
手指操作時，finger node（手指 / event5・6）有完整 BTN_TOUCH DOWN / MT_TRACKING_ID / MT_POSITION / UP正確
筆書寫 / 側鍵 / 筆尾 / 多指 / 四角 / 解析度tool type、座標、BTN_STYLUS、BTN_TOOL_RUBBER、雙 slot、16384/16384 全部到位PASS
底層結論：driver 並沒有把手指誤判成 stylus，兩條 input pipeline 分流正確。 換句話說，作業系統交給 APP 的資料是對的——手指就是以「FINGER」的身分送進來的。 所以 FW / driver 這一層不需要任何修改。

② 上層 APP — 手指攔截被「機型清單」擋掉，需修改邏輯

nNote 在 HandwriterView.onTouchEvent() 確實寫了「手指就不要出水」的攔截：

// HandwriterView.java · onTouchEvent()  (約 L656)
if (RefreshClass.isEinkHandWritingHardwareType() &&
        event.getToolType(0) == MotionEvent.TOOL_TYPE_FINGER) {
    // ↑ 手指 → 走手勢 / 不出水（這段才是正解）
    ...
}

但這個 if 的第一個條件 isEinkHandWritingHardwareType()，是用一份寫死的機型清單來判斷「這台是不是手寫機」：

// RefreshClass.isEinkHandWritingHardwareType()  ← 問題根源
return SystemProperties.get("ro.product.hardwareType","").equals(TYPE_E60Q60)
    || ... .equals(TYPE_ED0Q00)
    || ... .equals(TYPE_E70Q30)
    || ... .equals(TYPE_EA0Q00)
    // ……一長串舊機型……
    || SystemProperties.get("ro.product.device","").equals(TYPE_EA0P04);
// ⚠ 新裝置（本次 EA0T4A）不在這份清單裡 → 回傳 false

為什麼手指就出水了？（邏輯流程）

手指觸碰
OS 正確送出 TOOL_TYPE_FINGER
→
isEinkHandWritingHardwareType()
新機型不在清單 → false
→
整個 if 條件為 false
手指攔截分支被跳過
→
手指 event 落到繪圖 handler
→ 出水
真正原因：不是 FW，也不是「native 層接走 finger」（前一版報告的推測）。 而是 Java 層的攔截邏輯被機型開關 gate 住——新機型沒登錄，整段防出水程式碼形同未啟用。 這也說明為何 C1–C5（手指 / 手掌相關）會全部 FAIL：它們都走同一個被跳過的 gate。

修正方式

讓 isEinkHandWritingHardwareType() 對新裝置回傳 true。兩種做法：

做法內容適用
A. 加入機型清單把新裝置的 ro.product.device / hardwareType 加進判斷（如 TYPE_EA0T4A）須維護多機型、要精準控制時
B. 直接回傳 true確認本產品線都是手寫機，直接 return true;（如下圖現行改法）本機種全為 e-ink 手寫機，最簡單
// 現行修正（return true，舊清單註解保留）
public static boolean isEinkHandWritingHardwareType() {
    return true;
    /*  ……原本的機型清單保留作註解……  */
}
修正後預期：isEinkHandWritingHardwareType() 回 true → 手指攔截分支正常執行 → 手指走手勢、不再出水 → C1–C5 應全部轉 PASS。修改後請重跑 nNote 功能行為 C 區與 F 區回歸確認。

重點補充（回答主管三個直接問題）

Q：單點側鍵後當前行為？會切換橡皮擦嗎？
A：會。單擊側鍵會切換為橡皮擦（D1 PASS），raw 層 BTN_STYLUS 單擊呈成對 DOWN/UP。
Q：按壓側鍵後當前行為？會保持橡皮擦嗎？
A：會保持。按住期間維持橡皮擦、放開後恢復為筆（D2 PASS）。 唯一缺點：長按 + 拖曳時是「整段筆跡一次擦掉」，而非沿軌跡局部連續擦（D3 FAIL）——這是 app 橡皮擦行為要再調整的點。
Q：Touch FW 更新後，筆尾是否能有訊號？
A：有了 —— 這是本次 FW 更新的明顯改善。筆尾碰螢幕時 raw 已送出 BTN_TOUCH + BTN_TOOL_RUBBER + ABS_PRESSURE 且座標連續更新 （對比上次基準報告：筆尾完全沒有 BTN_TOUCH / BTN_TOOL_RUBBER）。
但 app 端目前對筆尾橡皮擦尚無反應（D4 FAIL）——raw 訊號到位、APP 邏輯尚未接，屬上層待補。
整體判讀：主管 9 個關注點裡，底層 raw 只有「邊緣未達滿幅(E2)」一項 FAIL，其餘 raw 全部正確。 APP 端的 FAIL（C 區出水、D3 整段擦、D4 筆尾無效果）都是上層邏輯待修，不是韌體問題。 其中 C 區出水的根因就是 ② 的機型 gate，一次修好即可全部轉 PASS。
