◆ 本期進度階段
本助手已完成建置並發布上線（僅限邀請），供資訊部與需求端試用。把使用者模糊的一段話（「想把費用請款 E 化」），透過 AI 對談潤飾與結構化，轉成 MIS 可受理的電子簽核需求單，並可輸出 JSON。
◆ 一句話定位

同仁用一段話描述想 E 化或想改電子簽核的流程；助手先潤飾確認「我理解你的意思是…」，確認後再拆成五區塊需求單、推論簽核流程，最後可輸出結構化 JSON 供 MIS 辦理。設計對齊需求端既有的需求細化平台流程，紀律沿用：AI 推測需標示、不覆蓋已修內容、決策由人。

◆ 核心功能
💬先潤飾再確認

不直接拆解，先用「我理解你的意思是…」回述，經使用者確認後才進入拆解；避免拆錯方向。

🧩五區塊需求單

說明、表單畫面設計、表單欄位（＊必填）、簽核流程、其他與待確認項目；缺漏自動列入待確認。

🔑簽核與核決推論

依關鍵字補簽核關卡；提到金額／請款自動加「核決權限」關卡與金額欄位，並依級距推論會簽到哪一層。

🗂️結構化 JSON 匯出

一鍵輸出乾淨 JSON（欄位／簽核／待確認＋來源標註），供匯進 MIS 或需求端平台。

◆ 實測對照 Live Demo

以下為實際在正式對話頁跑過的示範（示範資料為虛構去識別化）。情境：把「費用請款」E 化。點圖可放大檢視。

1先潤飾確認：「我理解你的意思是…」

貼上一段模糊需求後，助手不急著拆解，先回述理解的表單、初步欄位與簽核順序，並標示推測項；結尾主動問「這樣理解對嗎？」等使用者確認。

🔍 點擊放大
2確認後拆成五區塊需求單（含核決權限推論）

確認後產出完整需求單：欄位表標＊必填與型態／來源，簽核流程含開單者→主管→財務→核決權限；金額約 8 萬時推論「約需簽至總經理層級（推測，請確認）」，並強調實際級距以公司最新核決權限規定為準、不寫死。

🔍 點擊放大
3一鍵輸出結構化 JSON（可匯進 MIS／平台）

最終可輸出乾淨 JSON：欄位、簽核關卡、待確認項目，且每項標註 evidence（使用者提供 vs AI 推論）；正是未來把助手包成 API 銜接需求端平台的結構基礎。

🔍 點擊放大
◆ 驗收與資安

核心驗收通過：潤飾確認、五區塊、簽核與核決推論、JSON 匯出、以及錯誤回報動作端到端實打，皆已實測。與需求端既有平台的規格逐項吻合。核決權限屬公司內部制度，助手可依它推論簽核層級、但不整表輸出原文；分享範圍僅限邀請、給資訊部與需求端。

關於此助手（不隨週更新）
🧩核心價值與後續規劃▶
  • 定位：把使用者模糊的資訊／電子簽核需求，轉成 MIS 可辦理的需求文件；減少需求端與 MIS 之間反覆追問的溝通成本。
  • 戰略價值：需求端已自建需求細化原型平台，缺的是「需求理解引擎」（反問／潤飾／缺漏判斷／語意分類）；本助手正是這塊的活原型，指令成熟後可包成 API 供其平台呼叫。
  • 能力邊界：本版聚焦軟體組／電子簽核需求；硬體報修／設備申請另建。助手只建議、不替使用者拍板，缺漏一律列待確認。
  • 後續規劃：依試用回饋補強常見表單／流程模板；與需求端對焦平台 JSON schema 銜接，鋪路把指令包成 API（由對話工具直通後端服務化）。
