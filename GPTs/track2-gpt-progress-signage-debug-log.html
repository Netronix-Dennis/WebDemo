廣告機 SW Debug Log 分析工具

🖥️ 本機工具（非線上 GPT） 🔍 讀真實原始碼追因 📄 產出 HTML 報告 📚 知識庫會成長 ✅ 已用真實客訴 log 驗證

一、這是什麼

同仁把客戶回報的 log 丟給它，它會自動找出對應版本的真實原始碼， 把 log 的每一行對應回程式碼位置，指出錯在哪裡、為什麼會錯，最後產出一份 HTML 報告。

過去這件事要人工做：翻幾十萬行 log、猜是哪個版本、手動 checkout 程式碼、逐行比對。 一個案子動輒半天到一天。

為什麼這個不做成線上 GPT？

線上 GPT（軌2 其他專案）本機 Codex（本專案）
能讀公司程式碼？❌ 碰不到內網 repo✅ 直接 checkout 對應版本
能跑 git／grep？❌✅ 可跨檔追因
能處理 150MB log？❌ 貼不進去✅ 實測 147 萬行 32 秒
使用方式瀏覽器對話VS Code + Codex plugin

追因必須「看那個版本當下的程式碼」，所以只能走本機。

二、使用情境

誰在什麼時候用

客戶的廣告機出問題 → 現場收 log 回來 → 研發 SW 同仁 要找出原因。

同仁要做的事：把 log 丟過去，講一句話

分析這個廣告機問題：
問題簡述：客戶反應開機後畫面卡在 logo、圖片不更新
Log：/path/to/CaptureLog.zip
版本號不用給。App 開機就會把自己的版本印在 log 裡， 工具會自己抓（實測兩份不同來源的真實 log 都成功抓到）。同仁記錯版本反而會誤導分析。

吃得下哪些 log

來源樣子常見度
程式內建 CaptureLog一個 zip，裡面是 SD 卡結構，含 5 個輪替 log 檔（約 150MB）★ 最常見
Android Studio 匯出單一 txt，工程師自己從 IDE 存下來的常見
adb logcat 存檔單一檔偶爾
拆殼序列埠錄製拆機接線錄的，是唯一能看到 MCU 內部的方式少（特殊案例）

共 5 種格式會自動辨識，同仁不需要事先整理或轉檔。

三、核心原理：讓 log 自己指出程式碼位置

這個工具能成立，靠的是一個發現 —— 廣告機的 App 不是用一般的 log 寫法， 而是走自製的紀錄器，每一行 log 都自帶「哪個類別、哪個方法、第幾行」：

08-03 14:22:03.839  2143  2150 E SA0P10: MainActivity.onReceiveResult(2208): [onReceiveResult action:]
                                          └── 類別 . 方法 ( 行號 ) ──┘
好處一：對應是確定的
不用猜「這行 log 大概是哪段程式印的」—— log 直接寫了。
好處二：可以反過來驗證版本
到那個版本的程式碼第 2208 行去看，是不是真的有一句紀錄指令？ 對得上就是版本正確。
為什麼第二點很重要：行號只在正確的版本下才有意義。 版本錯了，工具會指著完全無關的程式碼講得頭頭是道 —— 那比不分析更糟。 所以每份報告最前面都會標版本一致性百分比，讓看報告的人知道能不能信。

四、完整流程

① 收到 logzip／目錄／單檔都行
② 抓版本從 log 自報的版本讀出來
③ 取程式碼自動 checkout 對應版本（唯讀，不動任何人的工作區）
④ 分層過濾147 萬行 → 只留相關的幾萬行
⑤ 對應＋驗證log 行 → 檔案:行號，並算版本一致性
⑥ 比對知識庫「這個問題看過，上次結論是…」
⑦ 追因Codex 讀程式碼判斷原因
⑧ 產出報告HTML，放在「分析報告」資料夾
⑨ 沉澱學到的寫回知識庫 → 下次更快

④ 分層過濾在做什麼

完整 log 裡大部分是 Android 系統本身的訊息，跟廣告機程式無關。而廣告機的程式又分三層， 各層的原始碼在不同的專案裡，必須分開比對：

App 18%
DA 26%
底層 19%
系統雜訊 37%
App 層 261,385 行 DA 層 371,098 行 底層 268,662 行 系統雜訊 527,323 行（擱置）

（真實 CaptureLog 實測數字，共 147 萬行）

五、最終產出：HTML 報告

報告產在專案的 分析報告/ 資料夾，檔名是 <log名>_<日期時間>.html。 直接雙擊用瀏覽器打開，不需要網路、不需要裝任何東西。

報告區塊內容
結論橫幅一句話講完根因
版本一致性百分比 + 判定，先看這個才知道報告能不能信
發生了什麼現象，每條標【確定】或【推測】
為什麼會發生因果鏈 + 原始碼片段（出錯那行高亮）
事件時序關鍵事件依順序排列
已知問題比對命中知識庫哪幾筆、上次的結論
建議下一步依優先序，給工程師參考
分析限制誠實列出哪裡資訊不足
報告格式強制「有依據」：每條研判都必須標明是【確定】還是【推測】， 並附上 log 行號與程式碼位置。寫不出沒有依據的結論 —— 這是刻意設計的， 避免報告看起來很有把握其實在猜。
個資提醒：報告會自動掃出 log 裡的 WiFi 密碼、MAC 位址、Token 樣式並警示 （某份真實 log 就命中 WiFi 密碼樣式 107 筆、MAC 42 筆）。但不會自動改寫原始 log， 因為改了會破壞追因證據。

六、知識庫：愈用愈準

每分析一次就把學到的東西寫回知識庫，下一次遇到同樣的現象會直接命中：

【KI-0007】外接 T-Con 偵測失敗 → 空清單操作 → 崩潰重啟迴圈
   狀態 known · 🌟 已證實 · 過去出現 1 次 · 本次命中 2 行
   典型現象：App 反覆崩潰重啟（約每 7 分鐘一次）
   該查什麼：① 先加空清單保護（一行止血）② 補錯誤處理 ③ 才查硬體

目前知識庫有 7 筆，其中 4 筆已由實際案例或團隊文件證實。 沒有這個「寫回」動作，工具就永遠停在第一天的水準。

最有價值的一欄是「工程師最後查出的真正根因」。 工程師拍板後回填，工具下次就能直接給出正確方向 —— 而不是重新推一遍。

真實客訴案例：完整找出根因

拿一份真實的客訴 log 測試，不告訴工具任何線索（連當時的情況都已經忘記）， 由 Codex 自己分析。結果它找出了完整的根因鏈：

1. USB 暫時斷開外接顯示控制器被移除
2. 太早檢查供電後只等 50 毫秒
3. 找不到裝置清單變成空的
4. 對空清單操作程式沒檢查就取第一筆 → 崩潰
5. 沒有錯誤處理可回復的錯誤升級成整個程式死亡
6. 重啟迴圈每 7 分鐘重複一次

關鍵是它推翻了直覺的判斷。表面看像是「硬體壞了」， 但它發現 USB 裝置每次崩潰後幾秒就回來且能正常使用 —— 所以不是硬體故障，是程式沒等裝置就緒。 這個差別決定了要去修程式還是去換硬體。

工具也同時排除了另一個容易誤判的方向，並在報告裡明講理由。 修復建議是「先加一行保護止血 → 補錯誤處理 → 再調時序 → 最後才查硬體」， 跟直覺相反但正確。

八、大使該如何使用

先確認一件事：這個工具需要公司內網。 它要去內網的程式碼伺服器抓原始碼，所以必須在公司內網或連上 VPN，並且有對應的存取權限。 沒有權限的話工具跑不起來 —— 這種情況請找研發（SW）協助。

如果你是要「了解／介紹」這個工具

  1. 看這份說明就夠了 —— 第一、二、五節是重點（它做什麼、怎麼用、產出長什麼樣）
  2. 想看實際產出：請研發同仁給你一份 分析報告/ 裡的 HTML，雙擊就能開

如果你是要「實際使用」

  1. 拿到交付包（一個 zip，約 120KB）並解開
  2. 第一次要初始化：執行 scripts/bootstrap_repos.sh
    它會自動把需要的三個程式碼專案抓下來（約 200MB，只需做一次）
  3. 丟 log 進去：scripts/analyze.sh <log路徑>
    或在 VS Code 裡直接跟 Codex 講（它會讀專案的作業說明自己執行）
  4. 開報告：到 分析報告/ 資料夾，雙擊最新的 HTML

使用上要知道的三件事

事項說明
先看版本一致性 報告最上面那個百分比。高＝可信；低＝先確認版本，別急著相信結論
根因由工程師拍板 工具的角色是加速定位，把範圍從幾十萬行縮到幾行。 最終判斷與修復方案仍由研發工程師決定
報告含客戶資訊 分析報告/ 裡的檔案會引用客戶 log 內容， 不要隨意外傳，也不進版本控制
