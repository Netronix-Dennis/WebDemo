一、這是什麼

同仁把客戶回報的 log 丟給它，它會自動找出對應版本的真實原始碼， 把 log 的每一行對應回程式碼位置，指出錯在哪裡、為什麼會錯，最後產出一份 HTML 報告。

過去這件事要人工做：翻幾十萬行 log、猜是哪個版本、手動 checkout 程式碼、逐行比對。 一個案子動輒半天到一天。

為什麼這個不做成線上 GPT？

線上 GPT（軌2 其他專案）本機 Codex（本專案）
能讀公司程式碼？❌ 碰不到內網 repo✅ 直接 checkout 對應版本
能跑 git／grep？❌✅ 可跨檔追因
能處理 150MB log？❌ 貼不進去✅ 實測 147 萬行 32 秒
使用方式瀏覽器對話VS Code + Codex plugin

追因必須「看那個版本當下的程式碼」，所以只能走本機。

三、核心原理：讓 log 自己指出程式碼位置

這個工具能成立，靠的是一個發現 —— 廣告機的 App 不是用一般的 log 寫法， 而是走自製的紀錄器，每一行 log 都自帶「哪個類別、哪個方法、第幾行」：

08-03 14:22:03.839  2143  2150 E SA0P10: MainActivity.onReceiveResult(2208): [onReceiveResult action:]
                                          └── 類別 . 方法 ( 行號 ) ──┘
好處一：對應是確定的
不用猜「這行 log 大概是哪段程式印的」—— log 直接寫了。
好處二：可以反過來驗證版本
到那個版本的程式碼第 2208 行去看，是不是真的有一句紀錄指令？ 對得上就是版本正確。
為什麼第二點很重要：行號只在正確的版本下才有意義。 版本錯了，工具會指著完全無關的程式碼講得頭頭是道 —— 那比不分析更糟。 所以每份報告最前面都會標版本一致性百分比，讓看報告的人知道能不能信。

報告格式強制「有依據」：每條研判都必須標明是【確定】還是【推測】， 並附上 log 行號與程式碼位置。寫不出沒有依據的結論 —— 這是刻意設計的， 避免報告看起來很有把握其實在猜。
個資提醒：報告會自動掃出 log 裡的 WiFi 密碼、MAC 位址、Token 樣式並警示 （某份真實 log 就命中 WiFi 密碼樣式 107 筆、MAC 42 筆）。但不會自動改寫原始 log， 因為改了會破壞追因證據。

每分析一次就把學到的東西寫回知識庫，下一次遇到同樣的現象會直接命中：

案例一：客戶回報反覆重啟

拿一份真實的客訴 log 測試，不告訴工具任何線索（連當時的情況都已經忘記）， 由 Codex 自己分析。結果它找出了完整的根因鏈：

1. USB 暫時斷開外接顯示控制器被移除
2. 太早檢查供電後只等 50 毫秒
3. 找不到裝置清單變成空的
4. 對空清單操作程式沒檢查就取第一筆 → 崩潰
5. 沒有錯誤處理可回復的錯誤升級成整個程式死亡
6. 重啟迴圈每 7 分鐘重複一次

關鍵是它推翻了直覺的判斷。表面看像是「硬體壞了」， 但它發現 USB 裝置每次崩潰後幾秒就回來且能正常使用 —— 所以不是硬體故障，是程式沒等裝置就緒。 這個差別決定了要去修程式還是去換硬體。

工具也同時排除了另一個容易誤判的方向，並在報告裡明講理由。 修復建議是「先加一行保護止血 → 補錯誤處理 → 再調時序 → 最後才查硬體」， 跟直覺相反但正確。

案例二：大使丟來兩份 log，沒有任何說明

這次同時拿到 Android 端與拆殼錄的 MCU 端兩份 log， 而且完全沒有告知發生什麼事。用的就是第九節那段開場 Prompt， 一句話都沒有多給。

1. 送出一筆長設定506 bytes 的裝置設定指令
2. 長度欄位溢位長度被寫進單一位元組 → 變成 0
3. MCU 收不到封包宣告長度 0，無法當有效指令
4. 呼叫不返回等不到回應，流程卡住

它做到三件很不容易的事：

  • 兩份 log 的時鐘不同源也能對照 —— 一份是錄製電腦的時間、另一份是裝置時間 （而裝置時鐘還回朔到 2000 年）。它沒有硬對時間，而是用指令內容與順序比對， 因此能斷定「Android 有送出、MCU 端完全沒收到」。
  • 把「可能」算成「確定」 —— 它讀出程式碼把長度寫進單一位元組， 算出 506 bytes 對齊後恰好產生會截斷成 0 的數值， 而 log 印出的中間值與計算完全吻合。
  • 自己找到旁證 —— 它在程式碼歷史裡翻到同一天就有人送出的暫時修正 （把設定縮短），等於團隊已經撞到同一個問題。
而且它反過來校正了工具的知識庫。 工具原本記載某個保護機制的門檻是「8 分鐘」，它從這份 log 讀出是 14 分鐘 —— 查證後發現那個門檻會隨韌體版本改變，工具把單一樣本當成了固定值。 知識庫已依此修正為「一律從 log 讀取，不要假設」。

這就是第七節「愈用愈準」的實際運作：分析會回頭修正工具本身。

九、大使該如何使用

先確認兩件事
  1. 需要公司內網 —— 它要去內網的程式碼伺服器抓原始碼，所以必須在公司內網 或連上 VPN，並且有對應的存取權限。沒有權限工具跑不起來 —— 請找研發（SW）協助。
  2. 需要幾個基本工具（開發機通常都有）： gawk、python3、PyYAML、git、unzip。
不用自己一項一項檢查。 工具每次執行都會先自動檢查環境，缺什麼會直接擋下來並告訴你怎麼裝， 一切正常時完全不出聲。也可以自己先跑一次：scripts/check_env.sh

為什麼要特別檢查：其中 PyYAML 缺了會讓 「已知問題比對」安靜地被跳過 —— 分析照樣產出報告，但少做了一半而你不會知道。 所以工具把它列為必要項，而不是提醒。

如果你是要「了解／介紹」這個工具

  1. 看這份說明就夠了 —— 第一、二、六節是重點（它做什麼、怎麼用、產出長什麼樣）
  2. 想看實際產出：請研發同仁給你一份 分析報告/ 裡的 HTML，雙擊就能開

如果你是要「實際使用」

  1. 拿到交付包（一個 zip，約 300KB）並解開 → 先看裡面的 快速上手.md（一頁，會告訴你先做什麼）
  2. 第一次要初始化：執行 scripts/bootstrap_repos.sh
    它會自動把需要的三個程式碼專案抓下來（約 200MB，只需做一次）
  3. 在 VS Code 打開這個專案資料夾，開啟 Codex，把下面那段 Prompt 貼給它（設定角色）
  4. 把 log 給它 —— 直接說「分析這份 log：路徑」即可
    也可以不用 Codex，直接跑 scripts/analyze.sh <log路徑>
  5. 開報告：到 分析報告/ 資料夾，雙擊最新的 HTML

Netronix 廣告機（E-Ink signage）的 Debug log 追因。使用者是研發 SW 同仁，

把 log 對應回**那個版本的真實原始碼**，指出關鍵錯誤、可能原因、下一步。
**根因確認與修復由工程師拍板**，你提供依據。

### ✅ 該寫
- **錯誤簽章**：類別、方法、訊息關鍵字／regex（讓下次能自動比對到）
- **機制**：這行 log 在什麼條件下才會被印出（讀碼得到的，最有價值）
- **該查什麼**：下次遇到，直接往哪裡看
- **版本範圍**：哪些版本有、哪個版本修掉的
- **工程師最後證實的根因**（🌟 最有價值，請務必回填）

### ❌ 不該寫
- **原始 log 內容**（可能含客戶個資／機密；也會讓檔案爆掉）
  → 只記「第幾行出現什麼簽章」，不貼整段
- **客戶名稱、序號、MAC、IP、WiFi 密碼**
- 沒有依據的猜測（要寫就標 confidence: code_read 或 hypothesis）

### confidence 兩級
  code_read  = 從真實原始碼推導出的機制（可靠但未經實機證實）
  confirmed  = 工程師實際查證過的根因（🌟 這才是最終答案）

「不該寫」那半邊同樣重要 —— 知識庫不存原始 log 內容， 只存錯誤特徵與機制。這樣它才不會變成一包客戶個資。

實際成效：目前 8 筆已知問題（5 筆已證實）。 而且有一次是分析反過來校正了知識庫 —— 工具原本把某個門檻記成固定值，實際案例證明它會隨韌體版本改變。

報告產生器的設計原則（scripts/report_html.py 開頭註解）
設計原則：
  1. **自足**：不連任何外部 CDN／字型／JS 庫
     （同仁可能離線、也可能直接雙擊開）
  2. **圖文並茂**：log 組成圖、時間軸、原始碼片段（命中行高亮）
  3. **格式強制誠實**：「研判原因」區塊只吃結構化 findings，
     每條都必須標 certainty(確定/推測) 並附 evidence，
     → 想寫沒依據的結論，格式上就寫不出來
  4. 淺色／深色都可讀（跟隨系統，也可手動切）

`certainty` 沒填、`evidence` 是空的，報告就會把那一條標成紅字警告。 `limitations` 欄位也是刻意設計的 —— 強迫寫下「這次哪裡資訊不足」， 而不是讓報告看起來什麼都知道。

實際案例二的報告就用了三級：【確定】、【推測（高信心）】、 以及誠實的【資訊不足】。
