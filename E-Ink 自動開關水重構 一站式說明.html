把出水/關水從 APP 散落判斷
下放到 Framework aDrawView

由 Framework 在 Hover / Stylus Down 時主動呼叫 aDrawView.isWaterSuspend() 詢問狀態。 預設用 View Tree 自動偵測 Dialog / OCR 等覆蓋物，APP 端僅需 Override 加入業務規則（工具類型、Noose 選取…）。 新增 UI 元件時，通常不必再回頭修 suspend 邏輯。

PAIN 01

window focus、page draw、FastView、Dialog、OCR、Popup、edited object、tool type… 散落於 nDrawHelper、NtxView、HandwriterView 多檔，每加一種 UI 就要回頭補一條判斷。

PAIN 02

呼叫鏈長 · 延遲累積

APP 端決定後，需經 AIDL 跨進程通訊呼叫底層，鏈路長且每段都可能延遲。Hover / Down 真正需要出水的瞬間，狀態可能還未生效。

APP → AIDL → Framework
PAIN 03

新增 Dialog / 工具 / 模式時，若忘了同步修改 suspend 條件，使用者會看到「Dialog 上仍在出水」、「OCR 過程墨跡誤觸發」等 bug — 屬於高頻復現的負債。

為什麼這個關係重要？
因為 NtxView 視覺上永遠在最上面（即使 Dialog 出現，墨跡仍畫在 Dialog 之上），所以 isWaterSuspend() 判斷的本質是「當前是否適合出水」（互動意圖），而非「是否被視覺遮擋」。
⚠
所以需要偵測誰？
只需偵測主 Window 內 比 [6] 高的覆蓋物：[7] ocr_fragment / [8] dialog / [9] alert_dialog。工具列因 layout 空間隔開不會誤判，PopupWindow 是獨立 Window 需另用 boolean flag。

判斷本質：互動意圖，不是視覺遮擋

SurfaceView 透明 + setZOrderOnTop 讓墨跡視覺上永遠在最上面 — 但 Dialog 出現時，使用者的觸控應送往 Dialog，不該出水。判斷的是「現在適合出水嗎」。

可放心採用 View Tree 預設實作

Framework 預設用 getGlobalVisibleRect() 矩形交集，能正確偵測到 dialog_container、alert_dialog_container、ocr_fragment_container；工具列因 layout 空間隔開，不會誤判。

例外：PopupWindow 仍需 boolean flag

PopupWindow 是獨立 Window，不在 Activity View Tree 中，無法用遍歷偵測。沿用 NoteWriterActivity.isPopupWindowShowing()，在 Override 中合併判斷。

§ 05

isWaterSuspend() 雙層責任分工

Default + Override
FRAMEWORK

預設實作 · super

遍歷 View Tree + getGlobalVisibleRect() 矩形交集，自動偵測上方可見 View 阻擋。涵蓋 Dialog / OCR / 任何 centerInParent 類覆蓋物。

  • 不需要白名單（工具列空間隔開不會誤判）
  • 對新增 UI 元件天然免疫 — 不必改邏輯
  • 由 Framework Team 維護
APP OVERRIDE

業務邏輯擴充

APP 端可 Override 加入結構偵測無法表達的業務規則：當前工具不是筆、Noose 選取中有物件、PopupWindow 顯示中…

  • 取代現有散落於 nDrawHelper / HandwriterView 的條件
  • 不通過時 return super.isWaterSuspend() 回退預設
  • 由 nNote APP 維護
MyADrawView.java
public class MyADrawView extends aDrawView {

  @Override
  public boolean isWaterSuspend() {
    // 規則 1：非筆跡工具 → 暫停出水
    int tool = ToolboxConfiguration
                  .getInstance()
                  .getCurrentTool();
    if (tool != Tool.BALL_POINT_PEN
        && tool != Tool.FOUNTAIN_PEN
        && tool != Tool.BRUSH
        && tool != Tool.PENCIL
        && tool != Tool.HIGHLIGHTER
        && tool != Tool.PARTIAL_ERASER) {
      return true;
    }

    // 規則 2：Noose 選取中 → 暫停
    if (hasActiveNooseSelection()) {
      return true;
    }

    // 規則 3：PopupWindow 顯示中 → 暫停
    if (NoteWriterActivity
            .isPopupWindowShowing()) {
      return true;
    }

    // 都未觸發 → 交回 Framework View Tree 偵測
    return super.isWaterSuspend();
  }
}

Framework 在這三個時機
主動詢問 isWaterSuspend()

When Framework Asks
Trigger 01

Hover 事件

偵測到筆正在靠近裝置，預先查詢狀態並準備好出水通道。

ACTION_HOVER_ENTER
Trigger 02

Stylus Down

筆真正落下接觸螢幕的瞬間，最後一次決定是否出水。

ACTION_DOWN + TOOL_TYPE_STYLUS
Trigger 03 · 補充

畫面結構變動

書寫中途彈出 Dialog 時，主動 re-evaluate，及時關水。

OnGlobalLayoutListener
建議補充

為什麼需要 OnGlobalLayoutListener？

僅靠 Hover / Down polling 是事件驅動的，若使用者正在書寫途中彈出 Dialog，下一個 Down 事件之前墨跡仍會繼續流出。註冊 GlobalLayoutListener 後，畫面結構一變動就重新詢問，補上動態覆蓋的缺口。

§ 08

風險評估與待確認事項

Risks · Open Questions
RISK 01 · 動態覆蓋

書寫中途彈出 Dialog 的延遲

若僅靠 Hover / Down 的 polling 機制，使用者正在寫字途中彈出的 Dialog，下個 Down 事件前墨跡仍會繼續流出，造成「Dialog 上有殘留墨跡」的視覺異常。
緩解 · 註冊 ViewTreeObserver.OnGlobalLayoutListener，畫面結構一變動就 re-evaluate；或由 APP 主動 notify Framework re-check。
RISK 02 · NtxView 遷移

surfaceCreated() 內含大量初始化

現有 NtxView 的 surfaceCreated() 中包含 pen type、stroke width、color 等工具初始化邏輯，遷移到 aDrawView 後需確保這些設定仍能正常運作、時序正確。
緩解 · Phase 2 提前盤點 surfaceCreated() 所有副作用，定義 aDrawView 的初始化 hook，必要時 Framework 提供對應 lifecycle callback。
RISK 03 · PopupWindow 偵測限制

PopupWindow 不在 View Tree 內

PopupWindow 是獨立的 Window 層級，不在 Activity 的 View Tree 中，View Tree 遍歷偵測不到。現有靠 NoteWriterActivity.isPopupWindowShowing() 的 boolean flag。
緩解 · APP 的 Override 中合併判斷該 flag，回退到 super 前先檢查。新架構需保留此機制。
RISK 04 · 執行緒安全

isWaterSuspend() 的呼叫執行緒

Framework 在 Hover / Down 時呼叫，可能在 Input Dispatch Thread；但 View Tree 操作（getGlobalVisibleRect）通常需在 UI Thread。跨執行緒呼叫有 race condition 風險。
緩解 · Phase 1 與 Framework Team 確認呼叫執行緒契約；必要時於 aDrawView 內快取近似結果並透過 Handler post 到 UI Thread 更新。

方向可行，請主管 Buy-in
啟動 Phase 1 Survey

從 APP 散落判斷下放到 Framework 統一決策。新增 UI 不必再回頭修 suspend 邏輯，呼叫鏈縮短，並透過 View Tree 偵測 + Override 取得平衡。
